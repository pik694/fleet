# Adopting sessions changed by another fleet process

- External-session adoption: the TUI reads sessions from SQLite exactly **once**, at startup (`loadSessions`), so a session created by another fleet process would be invisible until restart. `maybeSyncExternalSessions` (heavy worker pass, self-throttled to `adoptSweepInterval`=5s) diffs the table against the cycle's snapshot via the pure `unknownSessions` and sends `adoptSessionsMsg`; `handleAdoptSessions` re-checks `sessionByID` (the snapshot is taken at cycle start, so the Update goroutine is the only authoritative dedupe point) then mirrors `handleSessionCreateResult` minus `SaveSession`. **Removals ride the same sweep** (`externalRemovalsMsg`, #304): a session is dropped from memory when its row is gone **and** its tmux is dead (`goneSessions`) — the liveness half is what spares a session this TUI just created, whose tmux is up before its `SaveSession` lands. Pinned checkouts whose directory no longer exists (`missingDirs`, a definite not-exist only) are **hidden, never unpinned**: moved from `pinnedRepos` to `missingPins` in memory and restored when the directory returns, so a remount doesn't cost the pin — but only while SQLite still holds it (`externalRemovalsMsg.pinned`), since dropping out of the missing set also happens when the header delete unpins it. The message goes out **every sweep**, not only when the missing set changes: memory can drift while the set stays the same (unpin, then `u` before the next sweep). `fleet remove` itself still leaves its pin behind, like `d` on a session row; the hide is what clears a worktree deleted afterwards. Unlike a session the user just created, an adopted row arrives on a timer, so the cursor must not move: it's captured with `targetForCursor()` and restored by identity via `target.find` after the rebuild. No resurrection risk — `deferDelete` deletes the SQLite row immediately, ahead of the 5s undo window.
- External relaunch/suspend: another process (`fleet restart`/`resume`, a `fleet send` wake, `fleet suspend`) can give a known session a **new tmux session** or suspend it, and the TUI used to keep pointing at the dead one — reading it as an error, and pressing `r` there would start a second agent on the same conversation. `relaunchedElsewhere` (pure, beside `goneSessions`) finds them, and **direction is decided by liveness, not by which side differs**: this TUI's own relaunch also leaves memory and row disagreeing until the row is persisted, but then memory names the *live* tmux session, while another process's relaunch leaves memory on a dead one and the row on a live one. Two paths apply it: the 5s sweep (`sendExternalRelaunches` → `externalRelaunchMsg`), and **compare-before-clobber** in `updateAndPersistStatus` — a session whose tmux is gone on the way into `error` first has its one row read (`LoadSessionLaunch`) **before `UpdateStatus` runs**, because that reads a missing tmux session as a crash and acts at once (a crash dump), and the worker's persist of `error` would erase a CLI suspend's `suspended` within one fast pass, long before the sweep reads it. A session suspended *here* and woken elsewhere (`fleet resume`, a `fleet send` wake) is a relaunch like any other — this TUI's own suspend never renames the tmux session. Every adoption path skips a session with a relaunch in flight (`Session.Relaunching`): mid-`Restart` memory already names a tmux session that isn't up yet, which is exactly what another process's work looks like. A change also carries the tmux name memory had when the worker diffed (`fromTmux`), and the handler drops it if memory has moved on since — this TUI relaunching the session between the sweep and the message would otherwise be overwritten with the CLI's tmux session, orphaning its own agent where no later sweep could see it (both tmux sessions are up). `AdoptExternalRelaunch` resets in-memory hook state **without deleting the status file** (by then it may be the new agent's), and restarts at `starting` rather than trusting the row's status, which the worker may already have overwritten. In-place relaunches (`respawn-pane`, tmux name unchanged) need neither: hook ownership follows the new agent process once the old pid is gone.
