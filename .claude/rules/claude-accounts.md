# Multiple Claude accounts

- Claude accounts: `~/.config/fleet/accounts.json` (0600) records emails/orgs/config-dir paths; the logins themselves live in the macOS Keychain, one item per account dir. Per-account Claude Code homes: `~/.config/fleet/accounts/<8hex>/`
- Multi-account (Claude only, `internal/claudeaccount`): several Claude subscriptions, one per session, so a spent 5-hour window on one doesn't stall the fleet. The mechanism is **one env var** — `CLAUDE_CONFIG_DIR` (`claudeaccount.ConfigDirEnvVar`) pointing at a directory that holds that account's own claude.ai login — appended in `Session.sessionEnv()` (session.go), the single chokepoint already feeding `Start`/`Restart`/`RespawnClaude` via tmux `-e`. Each session therefore authenticates **exactly as a plain `claude` in a terminal does**: nothing is layered over anything, so claude.ai connectors, Remote Control and `/api/oauth/usage` all keep working.
- **Why not `ANTHROPIC_AUTH_TOKEN`** (which fleet shipped first and then replaced): it sits at auth precedence 2 and *displaces* the claude.ai login, so every session lost connectors and Remote Control and printed a banner saying so. The `claude setup-token` credential behind it is inference-only, which forced three separate workarounds — it can't name its owner (so accounts were keyed `account-<sha256(token)[:8]>`, and rotating a token minted a second identity that orphaned every session pinned to the old one), it can't read `/api/oauth/usage` (so quota came from a hand-rolled probe that POSTed to `/v1/messages` and read rate-limit headers, spending real quota to measure quota), and it can't be verified (so a refused token scored as *unknown* and won every `least_used` comparison). All three are gone. Measured, not assumed: `CLAUDE_CODE_OAUTH_TOKEN` is worse still — against 2.1.221 with a Keychain login present it is **ignored outright**.
- **Two config dirs hold two independent logins.** On macOS the Keychain service name is `Claude Code-credentials` plus, when `CLAUDE_CONFIG_DIR` is set, the first 8 hex of `sha256(NFC(dir))` — derived by reading the shipped binary and confirmed against a live login (`/tmp/cc-spike-a` → `Claude Code-credentials-5205b77d`, pinned by `TestKeychainServiceIsScopedToTheConfigDir`). That suffix is the whole mechanism. `Account.ConfigDir` is therefore stored verbatim and the path is random (`~/.config/fleet/accounts/<8hex>`), never derived from the email or label — the Keychain item is keyed by the exact path, so deriving it from anything renameable would orphan the login.
- Account dirs are **provisioned on every launch**, not just at add time (`Provision`): `projects/`, `skills/`, `plugins/`, `agents/`, `commands/`, `ide/` are symlinked back to the real `~/.claude`, `settings.json` is **copied** (so fleet's hooks ride along, and so a future per-account setting isn't silently global), and `mcpServers` + per-project `hasTrustDialogAccepted` are mirrored out of `~/.claude.json`. Sharing `projects/` is load-bearing: it holds the transcripts `--resume` replays and fleet reads for auto-naming, and it is what lets a session move between accounts and still resume the same conversation. Per-launch because the user's `~/.claude` keeps moving; a dir that captured its state once would drift into a subtly different environment. Not shared: the credential (the point) and `history.jsonl`.
- Account identity is **read, never guessed**: `claude auth status` reports `email`, `orgId`, `orgName` and `subscriptionType` for a real login. `Email` is the key and it is an actual address. `Store.Upsert` still matches on `OrgUUID` first (`indexOfLocked`), which now means "logging the same subscription in twice updates the existing account" rather than papering over a fingerprint rotation. A **blank org never matches**; a *different* org is a different subscription, never a correction.
- Add an account via `Ctrl+K → Manage Claude Accounts` → `a`, which opens a `fleetauth_` pane (deliberately not a `fleet_` prefix, so `tmux.ListSessions` can't mistake a login pane for an agent session) running `claude` with a fresh `CLAUDE_CONFIG_DIR`; the user runs `/login`. Completion is detected by **polling `claude auth status`** (`WaitForLogin`), not by scraping the pane — the old flow regex-matched `sk-ant-…` off the screen, coupling fleet to Claude Code's wording and allowing a half-success (login worked, capture missed) that needed a paste fallback. There is no paste path any more; `a` retries (the footer advertised a `p paste` key for a while after the flow was deleted — there was never a handler). An abandoned login's dir is removed rather than left for `Provision` to keep refreshing. The dialog also **owns the strategy**: `s` cycles `account_strategy` through `claudeaccount.Strategies`, with the value stated above the list. It sits here as well as in Settings because the strategy governs the list below it, and because it is what makes the `★` legible — a marker that appears only under `manual` reads as a property of the *account* rather than of the mode. The dialog picks the next value itself before emitting `accountStrategyMsg`, so its row repaints on the keypress rather than a round-trip later. Cycling to `manual` with nothing pinned toasts a prompt to press `⏎` (`manualNeedsDefault`): `Select` falls through to the automatic modes when the pin names no configured account, so that state is not broken, it is silently not doing what the mode says.
- Assignment (`claudeaccount.Select`, the one place strategy lives) via `account_strategy` config: `least_used_weekly` (**default**, most *weekly* headroom), `least_used_5h` (most 5-hour headroom), `waterfall` (configured order, skipping spent), `manual` (`default_account`, strict — it returns the chosen account **even when spent**, since quietly rotating away defeats the only reason to pick that mode). The least-used pair differ only in which window `pctOf` reads, via `rankWindow` → `Usage.Pct(Window)`. **Weekly is the default because the two windows fail on different timescales**: a 5-hour bucket refills this afternoon, so losing that race costs an hour, while a weekly bucket spent on Tuesday is gone until the following week — and ranking on the fast window lets every account's slow window drain in lockstep, which is the state that takes the whole fleet down at once. The pre-split `least_used` survives as an **alias, not a value**: `ParseStrategy` resolves it to weekly (same as unset) and `Strategies` — the ordered set both pickers offer — deliberately omits it, so cycling can never land on it. Mapping it to the 5-hour variant instead was rejected: it would make the *presence* of the key change behaviour, so the same file would behave differently depending on whether it was ever written. `StrategyLabel`/`StrategyLabels` live in `claudeaccount` for the same reason `Window.Name` does — the Settings cycler and the accounts dialog both render them, and two copies of the strings is how they stop agreeing. Selection-only: the accounts list, move picker and header readout still show the 5-hour figure regardless of strategy. Sessions are **pinned at creation**: Claude's prompt cache is per-account, so re-picking on every restart would drop the very thing a restart preserves. Forks **inherit** the parent's account (`forkSessionMsg.account`) — a fork resumes the parent's conversation and must authenticate as its owner.
- **A missing login is evidence; every other poll failure is not.** `FetchUsage` returns `ErrNotLoggedIn` for 401/403, the poll stamps `Usage.LoggedOut`, and `Select` drops those accounts via `dropLoggedOut` ahead of every strategy including `manual`. Without it an account with no login never gets a reading, so `pctOf` scores it at `unknownPct` (50) — which beats a healthy account at 59% and hands **every** new session the one account that cannot run, with no error anywhere. Categorically unlike *spent*, which `Select` still returns (soonest to reset) because a wait ends; a missing login doesn't, so emptying the candidate list is right and the caller falls back to the ambient login. `LoggedOut` is **live state on `Usage`, never persisted** — an account heals the moment it is logged in again (`handleAccountLoggedIn` replaces the usage entry outright, so the fix isn't invisible until the next poll). Shown as `✕ logged out` in the accounts dialog and the header readout, which renders it even with no reading at all.
- Restart **heals a pin that can't run** (`healAccountBeforeRelaunch`, called from `restartSession` and `resumeSelected`): if the pinned account was removed, is logged out, or is spent, the session is re-picked, persisted via `UpdateAccount` and announced in a toast — pinning protects a prompt cache, and there is no cache worth protecting on an account that can't answer. An **unpollable** account is left alone: fleet failing to reach Anthropic is not evidence against the login, and healing on it would rotate the whole fleet during an outage. A heal forces the **full `Restart()` path, never `RespawnClaude`** — `respawn-pane -e` layers over the environment tmux created the session with, so a move *to* the ambient login (which sets no variable) would inherit the old dir.
- Manual move: `.` → **"Move to Account…"** (`move_account` → `openAccountPicker`), a row-anchored dropdown (`internal/ui/account_picker.go`) built on the context-menu overlay pattern. Shows each account's **5-hour** figure — the header is deliberately quiet because it's always on screen, but here you're choosing *because* one is spent. The current account and any logged-out one render dimmed with the reason and are skipped by `j`/`k`. It **always relaunches**, and says so in the footer: the config dir is baked into the tmux environment at launch, so a move that only rewrote the record would relabel the row while the live process ran on the old account. Follows `contextMenuTarget`, not the cursor (`TestPickedAccountFollowsTheTargetNotTheCursor`).
- Account at creation (`A` → `SessionCreateDialog`, `internal/ui/session_create.go`): an **`Account` cycler row beside `Agent`**, so a session starts on the right subscription instead of being created wrong and moved — the only manual control before this was "Move to Account…", which pins *and relaunches* an existing session. `↑↓` move between rows, `←→` cycle the focused row's value, in the Settings detail pane's idiom (`renderDetail`); `tab` therefore means "next row" rather than the "next agent" it meant while there was one row. Options are **`Auto` first and preselected**, then each account with its 5-hour figure. Auto rides `sessionCreateMsg.account == ""`, which **already** means "let the strategy pick" — so nothing changes for anyone who just presses `A ⏎`, and no `accountSet` companion bool is needed (unlike `forkSessionMsg`, where `""` is a live identity meaning the ambient login). Auto's label names the account `account_strategy` would land on, resolved through **`selectAccountFor`, which `resolveAccount` now also calls**: two hand-built `SelectOpts` would drift, and a label naming a different account than the one billed is the lie the account labelling exists to stop telling (`TestAutoOptionNamesTheAccountResolveWouldPick`). Rows are built by `sessionCreateAccountRows`, modelled on `openAccountPicker` minus its `current` clause, and the dialog is a **pure function of what it was handed** — it never reads the store, so it tests without one. **Nil below two accounts**: with one or none every session runs on the same credential, so the row would be a constant — the rule `previewAccountLabel` already applies to the preview footer, and it keeps `A` untouched for the majority. On a **non-Claude agent the row goes inert, not hidden** (`accountRowActive`): hiding it would change the box height mid-keystroke, so it dims to `Claude only` — with the account name **removed**, since "yuval@brizz.ai  Claude only" reads as "this session runs on yuval@brizz.ai". The selection survives the round trip and `enter` sends `account: ""` there regardless. A **blocked account is landed on, dimmed with its reason, and refused** — a cycler can only honour "a disabled option is shown with its reason" by letting you reach one, so `⏎` is gated by `submitBlocker`, the one function the footer also reads, and the footer swaps to `<reason> — ←→ pick another`. It also drops its `↑↓ field` half whenever the Agent row is the only one that can move, so no dead key is advertised. Finally, an explicit account **skips `resolveAccount` and with it the per-origin allowlist**, so `handleSessionCreate` re-checks it at the chokepoint — the same check `resolveLaunchAccount` makes for an explicit `--account`, because a policy holding on one surface and not the other is worse than not having one.
- Quota comes from `GET https://api.anthropic.com/api/oauth/usage` — the cheap official route, available because a real login carries `user:profile`. Reading it consumes **no** message quota. The bearer is read out of that dir's Keychain item at poll time and never stored (`accessToken`, `security find-generic-password -w`). Values are already percent (0..100), unlike the rate-limit headers the old probe parsed, which were fractions — exactly one of the two ever needed scaling. Polled on the worker's heavy pass, throttled ≥180s per account — **except across a window's own reset** (`Usage.StaleAfterReset`), where the throttle is broken because the numbers have stopped describing the bucket they were read from: a spent account otherwise keeps reading spent for three minutes after it came back, with its countdown already at zero, which is exactly when its owner is watching. Bounded below by `AttemptedAt`, not simply "the reset is in the past" — a poll that *fails* at the boundary moves `AttemptedAt` past it, so the account backs off normally instead of retrying every tick against an endpoint that just refused. Failure is recorded rather than raised, so an unpolled account reads as *unknown*, not spent, and `least_used` degrades into waterfall order.
- **The CLI ranks on the same quota** (`claudeaccount.UsageForLaunch` ← `selectLaunchAccount`): `fleet worktree`/`fleet add` with no `--account` under a least-used strategy feed `Select` the TUI's readings via `~/.config/fleet/account_usage.json` (0600, no credential or error text), which the TUI's poll writes. A reading attempted within `MinPollInterval` is reused (`Usage.PollDue`, the TUI's throttle); otherwise all candidates are fetched in parallel under `CLIFetchTimeout` (3s). A reading older than `UsageCacheMaxAge` (2× the poll interval) stops ranking unless it shows the account spent. A quota failure never blocks a launch: stderr names each unread account and why. A re-login in the TUI replaces that account's entry with the login's own reading, or drops it (`ResetCachedUsage`), since the cache carries `LoggedOut`. `security` runs as `/usr/bin/security` because launchd may give no PATH.
- **`GuardConflictingAuth` matters more here than it did before.** A config dir's login sits at the *bottom* of the precedence order, so an ambient `ANTHROPIC_AUTH_TOKEN` or `ANTHROPIC_API_KEY` inherited from the user's shell silently overrides **every** account at once. tmux `-e` can add variables but not remove them, so a session can't scrub what it inherits — refusing loudly is the only honest answer. (fleet's own helper commands do scrub, via `configDirEnv`: fleet is often launched *from* a fleet session, and an inherited credential would make `claude auth status` report the wrong account.)
- Nothing in fleet stores a credential any more. `accounts.json` (0600) holds emails, orgs and directory paths; the logins live in the Keychain.
- Header readout (`internal/ui/accounts_header.go`, Appearance cycler `account_usage_style`): per-account usage top-right, **both windows every frame**, 5-hour first, each carrying **when that window resets** — a weekly figure without its horizon is unactionable. Two styles: `split` (default) gives each window its own countdown (`yuval 12%(2h) 34%(5d)`), `grouped` pools them (`yuval 12%/34% (2h/5d)`), `off` hides the strip. **It replaced a strip that moved on its own**: the readout used to show one window at a time and swap every 6s off the wall clock, *and* pick one of six densities by measuring what the breadcrumb left over — so a corner of the screen changed on a timer and reshaped whenever the cursor moved to a longer session title. Nothing here reads the clock now except the countdowns (`TestReadoutIsStableOverTime` renders at three offsets and demands byte-identical output). **Nothing names the windows — order does**, which is why 5-hour leads in every style and state; the countdowns cannot stand in for it, since a weekly window about to roll over reads `3h` exactly like a 5-hour one. The two styles are the **same width by construction** (four tokens plus five characters of glue either way), so neither is called "compact" and the fit ladder is style-independent — a narrower style would put the grouping back under the breadcrumb's control. That ladder is now **two steps**: drop the account names, then render nothing (it never falls back to the *other* style, for the same reason). A spent window is **not** special-cased into `spent <countdown>` any more — `quotaStyle` already paints anything at `ExhaustedPct` red, the same threshold `Select` stops handing the account out at, and the countdown sits beside it, so the state is legible without the chip changing shape *and* the other window's figure survives instead of being hidden. A reset that has **already passed** renders `now` rather than dropping the parenthetical (`100%(now)`): a countdown that vanishes at the moment it reaches zero leaves a red figure with no horizon in the one state where the horizon is the whole answer, and it is the chip changing shape on a timer. `now` is a claim that a fresh figure is one tick behind it, so it is **gated on `Err == nil && reset.After(FetchedAt)`** — neither the wall clock nor the reset time can promise that on their own. A *failing* poll advances `AttemptedAt` past the reset, which is what bounds the throttle break, so across an outage spanning a reset nothing re-polls and the strip would read `34%(now) 71%(now)` for its whole duration; and a poll that *succeeds* while returning an already-past reset (a 5-hour block is anchored to its first message, so a lapsed one can report its old `resets_at` for hours) is answering about a window it has already left. Both fall back to `""` — the bare figure this rendered before the countdown existed. An unknown reset drops as it always did. `✕ logged out` still takes the whole chip (no numbers to show) and renders even with no reading at all. In `grouped` the countdown parenthetical is **all or nothing** — pooled countdowns make `12%/34% (5d)` unreadable — while `split` drops each independently. Hidden below two accounts, or when even the nameless form would overflow the header. `account_usage_style` supersedes the legacy `show_account_usage` bool, of which only `false` migrates (→ `off`); the Settings cycler clears it on write.
- Per-origin allowlist (`allowed_accounts` config, keyed `origin:<key>` — the same keyspace as `collapsed_groups`/`snoozed_groups`; empty = all allowed). Deliberately **not** `.fleet.json`, which is committed — account policy is personal. Chosen over a per-origin *pin* because it composes with rotation: a pin has no good answer when its account is spent, while an allowlist does. Edited from `.` on an **origin header** → **"Allowed Accounts…"** (`internal/ui/allowed_accounts.go`), a row-anchored checkbox dropdown on the account picker's overlay pattern. Origin rows only: the key is per-origin, so offering it from a session or worktree row would put an origin-wide rule behind a control that looks like it acts on the row you're standing on. **Ticking every account deletes the key rather than storing the full list** (`config.SetAllowedAccounts`) — the two read identically today, but a stored list silently locks out the *next* account added, with nothing on screen to explain it; `a` toggles all, so it doubles as "remove the restriction". Zero ticked is **refused, not saved** (same rule as `SnoozeDialog`'s unparseable box): an empty list already means unrestricted in config, so saving it would do the opposite of what ticking nothing looks like it asks. A logged-out account stays **tickable here** — deliberately unlike the move picker, which can't move a session *onto* a dead login: this is policy, not availability, and "client work runs on the work subscription" stays true while that subscription is logged out. Rows are built from `Store.List`, so an email naming a removed account has no row and is dropped on save — opening and saving **heals** the stale-allowlist state `resolveAccount` refuses new sessions on. That heal is why the menu guard is **asymmetric**: `only one account` dims the row at `Len() == 1` *only when the origin has no stored allowlist*. Removing an account never prunes the allowlists naming it (`accountRemoveMsg` clears `default_account` and nothing else), so removing down to one account can leave an origin pointing at an account that no longer exists — which `resolveAccount` answers by refusing every session there, with the one UI that could clear it dimmed and `config.json` as the only escape. Deliberately **not** fixed by pruning on removal: empty *is* unrestricted, so pruning to empty silently widens the policy, and `AllowedConfigured`'s doc comment names "an account since removed" as precisely the case where falling back is "the one genuinely wrong answer". `openAllowedAccounts` mirrors the guard exactly, so a lit row can't dead-click and a dimmed one can't be reached another way. Sessions already pinned to a now-disallowed account are left alone; the allowlist governs *selection*, and the prompt cache it protects is per-account.
