# Status detection, hooks and per-agent behaviour

- Status detection: hook-based (primary, no time expiry) via Claude Code hooks + pane capture (fallback, ANSI-stripped)
- Agent team status: sub-agents don't fire hooks, so pane detection handles team states via structural checks (numbered menu `❯ 1.`+`2.`+ a menu footer — `Esc to cancel`, or `approve with this feedback` for ExitPlanMode plan-approval prompts; box-drawing `│`+`Waiting for team lead`); hook=running is never overridden to waiting by pane (avoids false-positives from code in scrollback)
- Background agents (`Agent` tool + `run_in_background`): the lead fires `Stop` (hook=finished) and parks until the agents re-invoke it, so the session would read idle/finished. `detectBackgroundAgentsRunning` (session.go) catches the in-flight dock rows (`◯ <type>  <desc>  <elapsed> · ↓ <tokens>`, rendered *below* the input box → scrollback-safe) and returns Running; `applyHookFinished` then overrides the finished hook → Running. Only the in-flight glyph `◯` matches, so the session self-clears to finished when the agents complete. Trade-off: a long background job shows Running for its full duration (chosen over hiding live work under idle).
- Hook status files: `~/.config/fleet/hooks/{session_id}.json`, written atomically via a **uniquely-named** temp file (`os.CreateTemp`) — hook handlers are one-shot processes and an agent can fire two at once (Codex asks permission per concurrent tool call), so a shared `<id>.json.tmp` let the loser's rename fail with ENOENT and could rename a torn write into place
- Hook handler: `fleet hook-handler` (invoked by Claude Code hooks, reads FLEET_INSTANCE_ID env)
- Hooks auto-installed into `~/.claude/settings.json` on TUI launch
- Multi-agent: per-session agent (Claude, Codex, OpenCode, or Copilot), chosen at creation (`A` key picker or `default_agent` config used by `a`). Stored in SQLite `agent` column; `internal/agent` owns binary name + launch command (`claude` / `codex resume <id>` / `codex fork <id>` / `opencode --session <id>` / `opencode --session <id> --fork` / `copilot --session-id=<id>`). Capability gates live on `agent.Type` — `SupportsEffort` (not OpenCode), `SupportsFork` (not Copilot: launching it with the parent's id would *take over* the parent's conversation, so `f`, its menu row and the `forkSessionMsg` handler all refuse, and `BuildLaunchCmd` drops a fork id rather than resuming it), `PreMintsSessionID` (Copilot only). Every agent switch in fleet ends in `default:` = Claude, so a new agent needs an explicit case at each one or it silently launches `claude` and gets Claude's pane heuristics. The list of agents itself is `agent.All` (pickers, `--agent` validation and help via `agent.Known`/`agent.NameList`, `default_agent`).
- Codex status: hook-driven with Codex-specific pane checks — Codex hooks are incomplete (a wait/approval prompt and a permission approval fire no hook), so a definite pane state overrides a stale hook (`codexPaneWaiting`→waiting, `codexPaneRunning`→running); an at-rest pane lets the hook decide running/finished/idle, and with no hook at all it settles to idle (see the Codex branch in `UpdateStatus`, session.go). Same pipeline as Claude — `fleet hook-handler` is agent-neutral (`hook_event_name`/`session_id`/`prompt` match Claude). Hooks installed to `~/.codex/hooks.json` (`InjectCodexHooks`, only when `codex` on PATH). Codex has no SessionEnd → `dead` from tmux pane-death. Claude's pane heuristics never run for Codex sessions — the pane checks are Codex-specific.
- OpenCode status: driven entirely by a generated TS plugin (no pane scraping); same agent-neutral `fleet hook-handler` pipeline. Unlike Claude/Codex declarative hook JSON, OpenCode's hook mechanism is a JS/TS plugin, so fleet writes `~/.config/opencode/plugin/fleet-status.ts` (`InjectOpenCodePlugin`, only when `opencode` on PATH; the resolved fleet binary path is baked in). **One file serves OpenCode 1.x and 2.x** through a single default export `{ id, server, setup }`: 1.x (1.4+) calls `server()` for the `event` hook, 2.x calls `setup(ctx)` and reads `ctx.event.subscribe()`. Neither accepts the other's shape (2.x refuses the old named `export const FleetStatus` with "Plugin must export a default definition with an id and an effect or setup function."; 1.x refuses a default export without `server()`), and both read the same config dir, so picking a template by `opencode --version` would break whichever install fleet didn't probe. Events map to fleet statuses via `spawnSync` (synchronous so the final status flushes before OpenCode exits, and ordering is preserved). 1.x: `session.status{busy}`→running, `session.idle`→finished, `question.asked`/`permission.asked`→waiting, `question.replied`/`question.rejected`/`permission.replied`→running. 2.x: `session.execution.started`→running, `session.execution.succeeded`/`.interrupted`→finished, `session.execution.failed`→error, `form.created`/`permission.asked`→waiting, `form.replied`/`form.cancelled`/`permission.replied`→running (verified against OpenCode 1.19.0 and 2.0.28). **Both prompt families are live and are not interchangeable**: `question.*` (1.x) or `form.*` (2.x) is the AskUserQuestion tool prompt, `permission.*` is a tool-permission prompt (only fires if the user set `permission: ask`; OpenCode defaults to allow-all). Watching only one is the stuck-at-running bug — the branches are additive, never a swap. On 1.x the `*.replied`/`*.rejected` listeners are belt-and-braces (OpenCode publishes `session.status{busy}` right after a reply anyway); on 2.x they are load-bearing, since 2.x publishes no `session.status` and a busy period has exactly one `started`. Sub-agent sessions have their own ids and are ignored by a root latch (the first session id the plugin sees, kept on `globalThis` because 2.x re-imports the file when fleet rewrites it, and a module-level latch would start over and could take a sub-agent). The latch filters lifecycle events (busy/idle/error) only: a permission or question prompt from a sub-agent, or a 2.x MCP form owned by `"global"`, still blocks the root's turn, so it is reported under the root (`reportAs`) — dropping it left the row reading running while the pane waited on the user. Since that merges several sessions' prompts into one row, open prompts are **counted** (on `globalThis`, like the latch): a reply reports running only when none is left open, busy is held back while one is (1.x re-announces busy after every reply), a reply with nothing open is dropped as stale (an interrupt can cancel a form after the turn already ended), and the turn's end clears the count. `TestOpenCodePluginOverlappingPrompts` runs the generated plugin under `node` to pin that sequence for both handlers. A 2.x `session.execution.failed` is followed by `session.idle`, as 1.x does, since nothing else ends that error. **On 2.x the plugin only reports from a private server**: 2.x runs plugins in a server rather than the TUI, and by default every TUI shares one background service that keeps the env of whichever client spawned it, so its `FLEET_INSTANCE_ID` can name the wrong pane. `setup()` stays inert unless the server is a private `serve --stdio` (`opencode --standalone`, any client with the background service turned off, `opencode run --standalone`, `opencode acp`). **That gate is load-bearing on 1.x too**: 1.19's newer core loader also calls `setup()` next to the `server()` hook, and only the missing `--stdio` keeps it quiet, so never swap the gate for anything a 1.x process can satisfy or 1.x reports every status twice. Status under 2.x defaults still needs either a version-aware launch with `--standalone` (1.x's strict yargs root exits on unknown flags, and 2.x's root no longer takes `--fork`/`--model`) or a 2.x TUI-entrypoint plugin, which runs in the pane's own process. No dir-trust seeding needed (OpenCode has no trust gate). No SessionEnd → `dead` from tmux pane-death. `UpdateStatus` routes OpenCode through `applyHookStatus` (shared with Codex); no pane heuristics run.
- Copilot status (GitHub Copilot CLI, `internal/session/copilot.go`, `internal/hooks/copilot_hooks.go`): hooks live in fleet's **own file**, `$COPILOT_HOME/hooks/fleet.json` (Copilot loads every `hooks/*.json`, so install writes it whole and uninstall deletes it — never a merge into `config.json`, which carries `//` comments and is rewritten by Copilot itself). The file needs a top-level `"version": 1`. The worker's hook-repair pass rewrites it when the fleet binary it names is gone (`RepairCopilotHooks`, same rule as Claude's: missing only, never merely different). Copilot's payload is camelCase and carries **no event name**, so each entry's command appends `--agent copilot --event <name>` and `handleHookHandler` normalises onto Claude's names (`userPromptSubmitted`→`UserPromptSubmit` etc.) so prompt capture and `PromptCount` run unchanged; registering the PascalCase keys instead also works but registering both **runs every hook twice**. Subscribed: `userPromptSubmitted`, `postToolUse`/`postToolUseFailure` (→running: approving a permission fires no hook, the tool finishing is the first sign), `notification` (→waiting only for `notification_type` `permission_prompt`/`elicitation_dialog`), `agentStop`, `sessionEnd`. **Never `permissionRequest`**: Copilot treats a failing one as a DENY, so a moved fleet binary would refuse every tool call in every Copilot session on the machine — and it fires for auto-approved tools too, so it was never a waiting signal. **Not `sessionStart`**: it fires lazily, *after* the first prompt, and would flip the first turn to finished. Copilot runs hooks **synchronously and for every Copilot session on the machine**, so the handler returns before `debuglog.Init` when `FLEET_INSTANCE_ID` is unset (a line per tool call would flood the debug.log) and skips the stale-file sweep on `PostToolUse`. Two gaps need out-of-band signals, both in `updateCopilotStatus`: a **cancelled turn** (Ctrl+C mid-turn, Esc at a permission prompt) fires **no hook at all**, so while the hook says running/waiting the worker reads `$COPILOT_HOME/session-state/<id>/events.jsonl` backwards (32KB, doubling while the window holds only bookkeeping, capped at 1MB — a `system.message` line alone measures 60–71KB) and a trailing `abort` (skipping `hook.*`/`model.*`/`session.*`/`system.*` bookkeeping) settles it to finished — `assistant.turn_end` alone is **not** an end, it also separates tool steps mid-turn; and **`/clear` and `/exit` both send `sessionEnd{reason:"user_exit"}`**, so `sessionEnd` is never `dead` — it maps to finished, and the pane decides: a hook has fired, `pane_current_command` is back at a shell (`tmux.IsShellCommand`) **and the owner Copilot process is gone** → dead (the pane alone misreads a live Copilot under a tcsh respawn, Ctrl+Z, or a split window — measured). Otherwise it was `/clear` — or `/exit` while another conversation is open, which Copilot switches to; the pane can't tell those apart, so the id stays on the closed conversation until the user types again. The reason still marks the hook as a SessionEnd, which keeps a dead session's crash dump from re-arming. A definite pane state (a `│ ↑/↓ to navigate · enter to select` / `enter accept · ctrl+d decline` menu → waiting — the box edge is part of the match, and footers are matched only in the last 3 non-blank lines (`copilotFooterLines`), so a reply quoting one can't pin the row, since `/theme`'s picker shows the same footer words outside a box and other pickers (`/resume`, `/model`, `/agent`, `/mcp`) were checked not to match, the `esc interrupt` working footer → running) overrides a stale hook, Codex-style; fixtures captured from a live pane are in `internal/session/testdata/copilot/`. **The conversation id is minted by fleet** (`launchWillResumeLocked`, first launch): `copilot --session-id=<uuid>` creates the session when it doesn't exist and resumes it when it does, so one form covers every launch and `r`/suspend work before any hook fires. That id is **authoritative** (`copilotHookAccepted`): Claude's same-process rotation rule does not apply, because one Copilot process holds several conversations — `/new` starts a fresh one **and keeps the old one open** (both hold `session-state/<id>/inuse.<pid>.lock`; no `sessionEnd`, no `session.shutdown`), and the Sessions sidebar runs more side by side. What moves the session is **the user typing**: the hook handler records the conversation of the last `userPromptSubmitted` as `prompt_session_id` in the status file (kept across later events; written for Copilot hooks only, so a `claude`/`codex` run as a tool can't claim it), and a foreign id is adopted only when it equals that. This covers `/new`, `/clear`, `/resume` and a sidebar switch, survives fleet being closed meanwhile (the file still says where the user typed), and a backgrounded conversation finishing its turn can't pull the session back. **Subagents fire `userPromptSubmitted` too**, under their own id, along with their tool and stop hooks — but a subagent logs into its parent's `events.jsonl` and never gets a `session-state/<id>/` of its own, while a real conversation always has one before its first hook runs (`session.start` precedes it). So `isCopilotSubagent` drops those hooks in the handler, before they can overwrite the user's prompt (auto-naming) or read as the conversation being typed in. First prompt is `--interactive="$FLEET_INITIAL_PROMPT"` (the `=` form; `-i "--x"` exits with "Invalid command format"). `Y` sends Enter alone for Copilot: its menus pre-highlight "1. Yes", and a typed letter can land in the "No, and tell Copilot…" text row. `fleet send`'s delivery check also accepts Copilot's collapsed paste, `[Paste #1 - 12 lines]` (matched squashed as `[Paste#`).
- Relaunch death rattle (all agents): `r`/respawn/suspend kill the old agent after `clearHookState`, and its shutdown can still fire a `SessionEnd` carrying the **same** conversation id the relaunch resumes. `clearHookState` keeps the old owner's pid as `retiredPID` and `UpdateHookStatus` drops any hook from it — the pid is the only thing that tells it apart. Claude recovered from this on its next `SessionStart`; Copilot fires none at launch, so its "hook fired + pane is a shell" rule would read it as a crash. A relaunch of an agent that never fired a hook has no pid to retire; for Copilot (which fires nothing at startup) a SessionEnd arriving before any other hook since the relaunch is that killed process's and is dropped, for 5s after the relaunch (`relaunchQuietTo`; the rattle lands within ~2s) — so only an `/exit` typed in those first seconds reads idle. The retired pid is honoured for 10s (`retiredHookWindow`), so a later agent the OS hands the same pid isn't silenced. `RespawnClaude` never SIGHUPs a pid whose pane is already at a shell — that Copilot exited, and its pid may be someone else's now. Copilot needs one more thing on relaunch (`awaitRetiredCopilot`): it holds a **per-process lock** on its conversation, and a busy Copilot takes **~1.8s** to exit after the kill (it runs its `sessionEnd` hook on the way out), so a new one started at once opens on a "Session in use — Resume anyway?" menu. `Restart` waits (capped at 5s, off the Update loop) for the old pid to exit — including, within 5s of a `Suspend`, the agent the suspend killed (a Copilot that has had a turn keeps its lock ~0.4–0.9s after the kill, measured; `resumeWaitPID`, never on the signalling respawn path); `RespawnClaude`'s `respawn-pane -k` kills and relaunches in one step, so for Copilot it first sends the old process SIGHUP itself. Both act only after `ps` confirms the pid is still a `copilot` binary, since it came from a hook and could have been recycled.
- Copilot trust: a folder that isn't trusted opens on a "Do you trust the files in this folder?" menu, **behind which no hook fires**. `EnsureCopilotDirTrust` appends the realpath to `trustedFolders` in `$COPILOT_HOME/config.json` — **not `settings.json`**, which was verified not to work (Copilot migrates a settings entry into config.json and drops it when config.json already has the key). The file is JSONC that Copilot owns, so the file is re-serialized (values kept and written without HTML escaping, keys sorted, comments other than the `//` header dropped); it runs in the launch's `tea.Cmd`, never the Update loop, under its own mutex (not Codex's `trustMu`) plus Copilot's own `flock(LOCK_EX)` on `config.json.trusted-folders.lock` (measured in Copilot 1.0.91; never deleted), so parallel `fleet wt` processes and Copilot itself can't drop each other's entries. Best effort: the lock is tried for 2s, and a stuck holder or a filesystem that can't lock means seeding unlocked — a lost entry shows as the trust menu, a launch that hangs doesn't show at all. The same step writes the hooks file if it's missing or stale, since startup installs it only when `copilot` was on PATH then, and the comment stripper is **string-aware** (`"https://github.com"` would otherwise be cut). Copilot's own trust propagation covers only worktrees it creates itself, so fleet seeds per session. A seed Copilot later overwrites shows as **waiting** (the trust menu shares the permission prompt's footer), never a silent idle.
- Codex trust: dir-trust pre-seeded to `~/.codex/config.toml` (`[projects."<path>"] trust_level="trusted"`, via `EnsureCodexDirTrust`) before launch; hook-trust is a one-time global TUI prompt the user accepts on first Codex launch (persists in config.toml `[hooks.state]`).
- Session resume: captures the agent's session_id from hooks (Copilot's is minted by fleet), uses `claude --resume <id>` / `codex resume <id>` / `opencode --session <id>` / `copilot --session-id=<id>` on restart
