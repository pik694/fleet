# tmux integration: attach, clipboard, extended keys, mouse, macOS TCC

- Tmux status bar configured per session with detach hint (ctrl+q)
- Attach uses PTY with Ctrl+Q intercept for clean detach (creack/pty + golang.org/x/term)
- Copy-to-clipboard: a copy-mode selection (drag, double/triple-click, keyboard copy) reaches the system clipboard via `tmux.EnsureCopyCommand` → `set-option -s copy-command <tool>` — `pbcopy` on macOS; on Linux the first *usable* of `wl-copy` (needs `WAYLAND_DISPLAY`) / `xclip` / `xsel` (need `DISPLAY`), display vars read from fleet's own env — the proxy for the client sessions get attached from (`clipboardCopyCommandFor`); with no display-reachable tool nothing is set, since tmux's default `set-clipboard external` already OSC-52s copy-mode selections. tmux's default copy bindings run `copy-pipe-and-cancel` with no arg, which pipes to `copy-command` **and** emits OSC 52 (`set_clip=1`) — the two are independent, not a fallback chain, so a `copy-command` that fails does not by itself lose the copy (only `set-clipboard off` does, by suppressing OSC 52). `copy-command` still matters because OSC 52 is what iTerm2 blocks by default and Apple Terminal doesn't support: a local pipe is terminal-independent. `copy-command` is a **server** option (fleet shares the user's tmux server, no dedicated socket), so it's set **only when unset**, leaving a user's own `copy-command` alone; it re-checks the live server on each call (no process-level cache) so a tmux server created fresh after a restart still gets it. Set `FLEET_NO_COPY_COMMAND` (truthy) to opt out entirely — e.g. when deliberately relying on OSC 52 (remote tmux → local clipboard over SSH). Called from `Start` (server exists) + the startup bootstrap (existing-session users)
- Extended keys (Shift+Enter): `tmux.EnsureExtendedKeys` turns on tmux `extended-keys` (+ appends `xterm*:extkeys` to `terminal-features`) so modified keys — most visibly `Shift+Enter` — reach the agent as a distinct sequence instead of collapsing to a bare `\r`; with tmux's default `extended-keys off`, `Shift+Enter` and `Enter` are the same byte, so Claude submits instead of inserting a newline. The pane sees `\x1b[27;2;13~`, **not** CSI-u `\x1b[13;2u`: `extended-keys-format` defaults to `xterm` and fleet deliberately leaves it alone (Claude accepts both, and the format is another shared-server option fleet doesn't own). tmux only sends the extended form to an app that **requested** mode 1/2 — Claude requests it whenever `TERM_PROGRAM` is on its allowlist, and tmux sets `TERM_PROGRAM=tmux` inside the pane, so the request fires regardless of the outer terminal (`pane_key_mode` shows `Ext 2` when it worked). Both are **server** options (fleet shares the user's tmux server): `extended-keys` is set to `on` unless it's already `on`/`always` — and since tmux `show-options -sv` returns the effective value (not empty-when-unset), this also overrides an explicit `extended-keys off` (use `FLEET_NO_EXTENDED_KEYS` to opt out); the exact `xterm*:extkeys` entry is appended to `terminal-features` only when absent (no duplicate piling, and not fooled by an `extkeys` feature on a different pattern like `screen*:extkeys`). The append is load-bearing only for terminals tmux can't name: `tty_default_features` auto-detects iTerm2/XTerm/mintty (all of which already carry `extkeys`) off XTVERSION, but **Ghostty is absent from every shipping tmux** (3.5a/3.6/3.7 — master only). Necessary but not sufficient — the **outer terminal** must honor xterm's `modifyOtherKeys` mode 2. iTerm2 does, unconfigured; **kitty never will** (it refuses `modifyOtherKeys` on principle and tmux ignores kitty's own `\x1b[>1u` request), so kitty needs a manual `map shift+enter send_text all \x1b[13;2u`. Claude's `/terminal-setup` is **not** the fix for iTerm2/Ghostty/kitty/WezTerm — per Anthropic's docs it targets VS Code/Cursor/Alacritty/Zed. **Version-gated** (`extendedKeysSafe`): skipped on exactly `3.5` (Alt+Backspace emits invalid bytes, Shift keys mis-encoded — tmux#4146/#4156, fixed in 3.5a) and on all of `3.6`/`3.6a`/`3.6b` (a fast key burst trips the assume-paste path and leaks the terminal's raw `^[[27;…~` bytes into the pane — tmux#5031, fixed in 3.7; Ubuntu 26.04 ships 3.6a). Both bugs live in the parser for keys *arriving from* the outer terminal — dead code while `extended-keys` is off, so they're bugs fleet would be *handing* users, on their own tmux windows, with nothing pointing back at fleet. tmux ≤3.4 requests mode **1** (`Eneks=\E[>4;1m`), so it likely gets no Shift+Enter benefit while still taking the server-wide change. Re-checks the live server each call like `EnsureCopyCommand`; called from `Start` + the startup bootstrap. The bootstrap path flips the option under **already-running** agents, which only record their mode request while `extended-keys` is on — an existing session can eat a `Shift+Enter` until it's restarted. Set `FLEET_NO_EXTENDED_KEYS` (truthy) to opt out — e.g. a terminal whose `Shift+Enter` you've bound differently, or a remote tmux you don't want reconfigured
- Warp can't drag-copy at all: Warp doesn't deliver mouse drag-selection to terminal apps (no tmux entry into copy-mode), so neither `copy-command` nor any tmux binding helps — unfixable from our side. `ApplyStatusBar` shows an amber "⚠ Warp doesn't support drag-to-copy (Warp bug)" on the bottom-right when `isWarpTerminal()` (`TERM_PROGRAM=WarpTerminal`)
- `mouse on` (set per session) is required for scroll: Claude/Codex render to the main screen (not the alternate screen), so with `mouse off` the wheel scrolls the outer terminal's scrollback (stale frames) instead of session history. Cost of `mouse on` is that native click-drag selection needs a terminal modifier (Shift; Option in iTerm2)
- Mouse (`internal/ui/mouse.go`): fleet reports the mouse in **cell-motion** mode (DECSET 1002 + SGR 1006), set on the `tea.View` by `Home.chrome`. Click a sidebar row to select it, double-click to activate it (`activateCursorRow`, the literal body of the Enter handler, so attach / resume / focus-split / toggle-group can't drift from the key), wheel to scroll, and click an entry in the context menu, command palette, snooze picker, account picker or allowed-accounts editor to run it. `FLEET_NO_MOUSE` opts out, like `FLEET_NO_COPY_COMMAND` and `FLEET_NO_EXTENDED_KEYS`. **Reporting was deliberately off until now (#268) and the reason has not gone away**: v2's eventLoop calls `View()` after *every* message and there is no click-only mouse mode, so one trackpad flick is ~300 `MouseWheelMsg`/sec, each buying a full compose — measured at 220% CPU. Two things hold it off, both in `Update`/`View` rather than in any handler: a mouse message is the only kind that does **not** mark `viewDirty`, so an event nothing acted on is served the cached frame (`Home.screen`); and one that *does* act repaints at most once per `mouseRepaintInterval` (16ms) with a trailing `mouseSettleMsg` so the settled state still lands. **The wheel scrolls `viewOffset` and never the cursor** — every cursor move fires `fetchPreviewForSelected`, which forks a `tmux capture-pane`, so a wheel bound to j/k would fork hundreds of processes per flick; scroll to look, click to select. Geometry is **recorded at render, never re-derived**: `renderBody` writes `h.layout.sidebar` per layout branch (all three put content at `sidebarContentTop`=2, the constant `contextMenuAnchor` inverts) and `composeScreen` writes `h.layout.overlay` where it already knows the box's x/y. Row maps are built by each dialog's own `View` as it emits rows (`overlayRowMap`) because the palette interleaves section headers, a `recent` label and blank spacers with its results — nothing but that loop knows which line a row got, and `sidebarWindow` is shared with `RenderSidebar` for the same reason (the `… N more below` indicator sits exactly on the first index a naive `viewOffset + row` returns). Activation is **the dialog's own key**, returned by `ClickRowAt` and replayed through `routeToModal`: enter in a menu, **space** in the allowed-accounts editor (where enter *saves*, so a menu-style click would store whatever happened to be ticked), and nothing on the snooze dialog's custom-duration row (enter there means "snooze for what I typed" and the box is empty when you click into it). A click outside an open overlay closes it via its own Esc; nothing falls through to the sidebar behind, which is still painted because the dropdowns deliberately don't dim. Clicks are **inert while the drawer is typing or a split is focused** — `j`/`k` can't move the sidebar there either, and a click that did would point the highlight at one session while the keys go to another; the wheel stays live, since scrolling is looking. Drag, motion and release are swallowed. Not covered: full-screen dialogs, the preview and drawer bodies (neither has scrollback), and drawer tabs
- macOS TCC-blocked folders: sessions/shells under `~/Documents`, `~/Desktop`, `~/Downloads` fail with "Operation not permitted" because tmux daemonizes into its own TCC "responsible process" and loses the terminal's Full Disk Access grant (unfixable from our side — the access happens in the tmux server, and there's no API to request a folder prompt for a CLI). fleet probes actual access lazily via `tmux.DirAccessBlocked` (a `run-shell` `ls` inside the server, so it reproduces the pane's attribution — not fleet's own process; cached per protected root per launch in `handleSessionCreate`/`forkSessionMsg`/`createShell`) and surfaces a `tipRecurring` (`tipTCCBlockedID`) pointing to a `Ctrl+K → "Open Full Disk Access Settings"` command that deep-links the FDA pane. Opt out with `FLEET_NO_TCC_WARNING` (remote-tmux/SSH)
